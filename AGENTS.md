# AGENTS.md

## Setup commands
- Install frontend deps: `npm install`
- Install functions deps: `npm --prefix functions install`
- Start dev server: `npm run dev`
- Start Firebase emulators: `npm run emulators` (requires firebase-tools >= 15.x globally; 14.x crashes every function worker at startup because it calls `functions.config()`, which throws under firebase-functions v7). Imports/exports `emulator_data/` on start and clean exit.
- Snapshot emulator data without shutting down: `npm run emulators:export` (hits the Emulator Hub on :4400 while running). Exports write a `firebase-export-*` temp dir then rename it; on Windows a file watcher holding the temp dir makes the rename fail with EPERM after the old dir is already deleted (recover by renaming/copying the temp dir to `emulator_data`). `**/firebase-export-*/**` and `**/emulator_data/**` are excluded in `.vscode/settings.json` (`files.watcherExclude`) and `vite.config.ts` (`server.watch.ignored`) to prevent this — keep those exclusions.
- Start dev server against emulators: `npm run dev:emulator`
- Run frontend tests: `npm run test`
- Run functions tests: `npm run test-functions`
- Run Firestore/Storage security rules tests: `npm run test:rules` (needs the Firebase CLI and Java 21; starts the firestore and storage emulators under project `demo-tuneteaser`)
- Build frontend: `npm run build`
- Build functions: `npm run build-functions`

## CI
- `.github/workflows/ci.yml` runs on pushes to `main` and on PRs, using Node 22: frontend `tsc --noEmit`, `npm run lint`, `vitest run`, and `vite build`; functions `npm run build` and `npm test`; a `rules` job installs Java 21 and `firebase-tools@15.34.2` and runs `npm run test:rules`. On PRs only, `actions/dependency-review-action` fails if the PR adds a runtime dependency with a high or critical advisory. There is no `npm audit` job: existing advisories are tracked by Dependabot alerts and security updates (enabled in repo settings, along with malware alerts).
- `.github/dependabot.yml` opens weekly grouped npm minor/patch updates for `/` and `/functions` with a 7-day release cooldown. npm major version updates are ignored (do them by hand with the migration guide); security updates still open regardless.
- Local Node is v24 (npm 11), but CI and Cloud Functions use Node 22 (npm 10). npm 10 is stricter about lockfile/peer mismatches, so after dependency changes verify with `npx -y npm@10 ci --dry-run` in a temp copy of `package.json` + `package-lock.json`. Frontend TypeScript must stay on 5.x for now: `vite-tsconfig-paths` -> `tsconfck` peers `typescript ^5`.

## Code style
- TypeScript strict mode
- Prefer existing MUI, styled-components, and shared `src/index.css` styles before adding UI dependencies
- Keep Cloud Function-controlled writes authoritative for leaderboard, usernames, multiplayer state, and Spotify imports
- Use `src/utils/logger.ts` (`logger.log`/`warn`/`error`) instead of `console.*`: log/warn are dev-build only and nothing emits in tests (`import.meta.env.MODE === 'test'`)

## Architecture notes
- Solo and multiplayer rounds are server-run. The client never receives the answer before a round ends; do not reintroduce client-side guess matching or point calculation. Solo callables live in `functions/src/soloRounds.ts`; there is no `submitLeaderboardScore`. `startSoloRound` writes the round doc in a transaction ordered by a `requestedAtMillis` field, so a slower earlier-issued start (for example an abandoned client prefetch) cannot clobber a newer round; keep that check if the write ever moves.
- Shared server game rules: `functions/src/answerMatching.ts` (Unicode-aware normalization, guess matching, points), `functions/src/playlistTracks.ts` (playlist loading for featured, saved, and guest Storage-only playlists), `functions/src/itunesPreview.ts` (timeouts, batched lookups, Firestore preview cache). `pickTrackWithPreview` resolves every attempted candidate and picks uniformly among `found` results; do not short-circuit on the first cache hit or lookup success, because warm cache entries then capture almost all picks (a small "same songs" oligopoly). Callable helpers are in `functions/src/callableUtils.ts`; new modules must not call `getFirestore`/`getStorage`/`getAuth` at module top level because `index.ts` calls `initializeApp()` after imports.
- Spotify is permanently in Development Mode: use `/playlists/{id}/items` (max limit 50, parse both `item` and `track` entries), per-ID `/tracks/{id}` lookups, and search `limit` 10 with pagination. Playlist contents and other users' playlists may be refused by Spotify; surface the custom-playlist fallback. Spotify OAuth login was removed; `clearLegacySpotifySession()` in `src/utils/auth.ts` clears old browser tokens at startup.
- `firebase.json` header rules: Firebase applies the last matching rule, so keep the general `**` rule before `/assets/**`. When adding an external origin, update the CSP there too (Umami needs `cloud.umami.is` in `script-src` and `connect-src`, plus `gateway.umami.is` in `connect-src` for event sends).
- Analytics: Umami lives in `src/utils/analytics.ts`; `initAnalytics()` injects the script only in production builds, and `trackEvent()` is a no-op when Umami is absent or blocked.
- Profanity: `functions/src/profanity.ts` rejects offensive usernames and room names (`containsProfanity`) and masks multiplayer playlist names (`censorProfanity`).
- `src/hooks/usePreviewPlayer.ts` stops snippets by audio position (`currentTime`), not wall-clock time, so buffering stalls do not shorten the scored snippet; keep it that way. It has a single-slot `preloadPreview(url)` that the next `playPreview` with the same URL reuses. `positionMs` only advances on `timeupdate` ticks (~4 Hz); `SnippetProgress` animates its fill to 100% over the *remaining* time with the Web Animations API, recreating the animation on each tick so it stays synced to position and freezes during stalls (driven by `isAdvancing`, which is set once the audio position provably advances and cleared on `waiting`/pause). When playback leaves the advancing state it settles to the new width (for example back to empty after a snippet) with a short WAAPI animation driven by `lastRenderedWidthRef`; that ref is captured with `getComputedStyle` inside the effect cleanup, which runs after React has already written the new base width — so every animation must use `fill: 'forwards'` or the capture reads the already-reset value. Do not replace any of this with a fixed wall-clock CSS transition, which runs ahead of the audio; the fill has no CSS transition on `width` by design. `useGameLogic` prefetches the next solo round when a round ends and discards it on playlist change or after 25 minutes (the server round TTL is 30).
- When a solo round ends, `useGameLogic` auto-plays the full ~30s preview on the `GameResult` screen (`playResultPreview`, `RESULT_PREVIEW_MS`); it goes through the same `usePreviewPlayer` instance, so the `pause()` calls in `startRound`/`handleSelectNewPlaylist` and the unmount cleanup already stop it when the player moves on. A `NotAllowedError` from a browser autoplay block is treated silently rather than as a playback error, so the result screen's play/stop toggle remains the fallback.
- Game keyboard shortcuts (Space play, Esc give-up confirm, N next track on the solo result screen, Enter focuses the guess field) go through `src/hooks/useGameShortcuts.ts`; keep Space/N/Enter ignored on editable and interactive targets (once the guess field has focus, Enter submits via the input's own handler). Disable them while any dialog over the game is open (`ActiveGame`/`GameResult` `shortcutsEnabled`); otherwise Esc reaches both the dialog and the give-up handler.
- In-app navigation away from an active solo round goes through `NavBar`'s `onNavigate` (also passed to `ProfileMenu`'s Settings link). `Home` uses it to show the "Leave this round?" confirm, and `Multiplayer` uses it to leave the lobby first. New nav links or menu links must route through `onNavigate` instead of plain `Link` navigation. The `ActiveGame` header Back button calls `onBack`, which `Home` wires to `handleNavNavigate('/home')`, so it reuses the same leave-confirm and `returnToPlaylistPicker` path.
- Guest auto sign-in is centralized in `src/hooks/useGuestAutoSignIn.ts` (used by Home, Playlists, PlaylistImportSpotify, Multiplayer) and `src/utils/guestSignIn.ts`. The hook signs in only when the page never observed a user that mount: a `user -> null` transition is a sign-out (possibly synced from another tab, since Firebase Auth shares sessions via localStorage) and must not recreate the session, or the signed-out tab's Login page bounces back into guest mode. `signOutExplicitly()` additionally writes a `tuneteaser:guestSignOutAt` localStorage marker so `signInAsGuest()` stays suppressed in other tabs and across remounts for 60 s; deliberate entry points (Login's Play as Guest, Multiplayer's create/join `ensureSignedIn`) call `clearGuestSignOutMarker()` first, and a session whose `lastSignInTime` postdates the marker clears it. Keep automatic sign-in behind `signInAsGuest` — raw `signInAnonymously` bypasses all of this.
- Premade playlists are defined twice: `src/utils/guestData.ts` (client cards, `genres`/`decades` tags, autocomplete tracks) and `functions/src/premadePlaylists.ts` (server track source). Keep their track arrays identical.
- `public/theme-init.js` must load at the start of `<body>` (it needs `document.body`); dark mode styles use `body.dark-theme`.
- `functions/tsconfig.json` sets `rootDir: "src"` explicitly (required by TypeScript 6 editors); output stays at `functions/lib/index.js`.
- Firestore TTL deletes expired docs on the Timestamp `expiresAt` field for collection groups `itunesPreviewCache`, `leaderboard/{uid}/dailyPoints`, `callableRateLimits`, and `leaderboard/{uid}/recentScores`. Manage policies with `gcloud firestore fields ttls update` in Cloud Shell; the Firebase console has no TTL UI. Do not reintroduce numeric `expiresAtMillis` on these docs; solo round state still uses `expiresAtMillis` for its own expiry check, which is unrelated to TTL.

- Multiplayer repeat avoidance mirrors solo: `startNextMultiplayerRound` excludes `playedTrackIds` persisted on the room doc (with `playedPlaylistId`), resetting when every playable track has played, on round 1, or on playlist change. The fields clear when a winner ends the game and on return to lobby.
- Scheduled multiplayer jobs filter and order by deadline and page through results with `processQueryPages` (batches of 50, 40s budget). Their composite indexes live in `firestore.indexes.json`; deploy indexes (`firebase deploy --only firestore:indexes`) and let them build before deploying functions that use new queries.

## Testing notes
- Rules tests live in `rules-tests/` with their own `vitest.config.ts` (node environment) and are excluded from the root `vitest run`. `@firebase/rules-unit-testing` v6 contexts return the compat SDK (`.doc()`, `.ref().put()`, `.getMetadata()`; no `getBytes()`). When changing `firestore.rules` or `storage.rules`, add or update a case there.
- CI has no `.env`, so any test that imports `src/backend/FirebaseConfig` (directly or through a util) must `vi.mock('../backend/FirebaseConfig', ...)`, or it fails with `auth/invalid-api-key`. Reproduce locally with `VITE_FIREBASE_API_KEY= npx vitest run` (process env overrides `.env`).
- A full frontend `vitest run` can hit intermittent 5s timeouts or "Failed to start forks worker" errors under load (TODO MED-26). Re-run the failing files alone before treating them as real failures.
